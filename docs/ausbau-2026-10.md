(`extensions/bluebranch/chatbot`) und das WordPress-Plugin `bluebranch-chatbot`

## Entscheidungen

- **Fragen, Antworten und Feedback liegen lokal im CMS** (Contao-Tabelle `tl_chatbot_log`,
  WordPress-Tabelle `{prefix}bluebranch_chatbot_log`), einsehbar und exportierbar im
  Contao- bzw. WP-Backend. Nicht in der API, nicht im API-Frontend.
- **Lastwarnung der API nur für Admins** (Rolle `ADMIN`, Opt-in im Profil).

## Gemeinsame Schnittstellen (Contao und WordPress gleich)

### Antwortstrom: Ereignis `meta`

Der CMS-Proxy reicht den Strom der API wie bisher durch und **liest dabei mit**: Aus jedem
`data:`-Block mit `answer` setzt er die Antwort zusammen, `sources` merkt er sich. Am Ende,
vor `event: end`, schickt er – nur wenn Feedback für das anfragende Modul aktiv ist –

```
event: meta
data: {"ref":"<32 Hex-Zeichen>"}
```

`ref` ist zufällig (`random_bytes(16)`) und die einzige Kennung, über die der Browser später
Feedback geben kann. Laufende IDs werden nie herausgegeben – sonst ließe sich fremdes Feedback
überschreiben.

- **Speichern an:** Zeile wird beim Stream-Ende geschrieben (mit `ref`).
- **Speichern aus, Feedback an:** Frage/Antwort liegen serverseitig in der Session (Contao,
  höchstens 20 Einträge) bzw. einem Transient (WP, 2 h) unter `ref`. Erst wenn Feedback kommt,
  wird daraus eine Zeile.
- Abgelehnte Anfragen (HTTP ≥ 400) und leere Antworten werden nicht gespeichert.
- „Inhalt zusammenfassen“ schickt den Seitentext als Frage mit; gespeichert wird stattdessen
  der Platzhalter `[Seite zusammenfassen]` (Flag `summarize: true` im Rumpf).

### Feedback-Route

| | Contao | WordPress |
|---|---|---|
| Route | `POST /bluebranch/chatbot/api/v1/feedback` | `POST /wp-json/bluebranch-chatbot/v1/feedback` |
| Schutz | Sitzungs-Token im Header `X-CSRF-Token` | Antwort-Token (`bb_token`) |
| Rumpf | `{"ref": "…", "rating": "up"\|"down", "comment": "…"}` | dito |

Regeln: `ref` muss `/^[a-f0-9]{32}$/` sein; `rating` nur `up`/`down`; `comment` nur bei
`down`, Tags entfernt, Steuerzeichen (außer Zeilenumbruch) entfernt, höchstens 1000 Zeichen.
Wiederholtes Feedback zur selben Antwort überschreibt (Daumen umentscheiden geht). Ratenlimit
je Sitzung bzw. Client. Ausgabe im Backend immer escaped; im CSV werden Zellen, die mit
`= + - @` oder Tab beginnen, mit `'` entschärft (Formel-Injection in Excel).

### Tabelle

| Spalte | Inhalt |
|---|---|
| `id` | laufend |
| `tstamp` / `created_at` | Zeitpunkt der Frage |
| `ref` | char(32), eindeutig |
| `root_id` (nur Contao) | Startpunkt – welche Website |
| `page_id` / `post_id` | Seite, auf der gefragt wurde |
| `source` | `widget`, `ask`, `search` |
| `language` | Sprache |
| `question` | Frage (E-Mail-Adressen und Telefonnummern maskiert) |
| `answer` | Antwort (Markdown) |
| `sources` | JSON `[{title,url}]` |
| `rating` | `''`, `up`, `down` |
| `comment` | Freitext bei 👎 (maskiert wie die Frage) |
| `feedback_at` | Zeitpunkt des Feedbacks |

**Keine** IP, kein User-Agent, keine Session- oder Nutzerkennung. Was Besucher selbst
eintippen, kann trotzdem Personenbezug haben – deshalb die Maskierung und ein Hinweis
„Bitte keine persönlichen Daten eingeben“ am Kommentarfeld. Aufbewahrung einstellbar
(Tage, Standard 180, 0 = unbegrenzt), täglicher Bereinigungslauf.

### Verlauf im Browser (Punkt 5)

Eintrag im `localStorage`: `{role, content, time, sources?, ref?, rating?, pending?}`.
Die Antwort wird **während** des Streams laufend (gedrosselt) gesichert mit `pending: true`.
Wird die Seite mittendrin verlassen, steht nach dem Neuladen die Teilantwort mit dem Hinweis
„Antwort unterbrochen“. Quellen und Feedback-Zustand werden mitgesichert und nach dem Laden
wieder angezeigt.

### Chat-Export (Punkt 4)

Knopf im Kopf des Widgets, Auswahl `.txt` oder `.vtt`, erzeugt im Browser (Blob, kein
Serveraufruf). TXT: `[HH:MM] Sie: …` / `[HH:MM] <Botname>: …`. VTT: `WEBVTT`, je Nachricht
ein Cue ab Start des Chats mit `<v Sie>`/`<v Botname>`; `-->` und Leerzeilen im Text werden
entschärft, `<`/`&` escaped.

### Quellen ohne URL

Quellen ohne (sichere) URL werden nicht mehr angezeigt – Zusatzinhalte (Punkt 7) haben keine
URL, und ein Dateiname als Quelle hilft Besuchern nicht weiter oder verrät interne Namen.

## Punkt 6 – Zeitgesteuerte Inhalte in Contao (Befund)

| Fall | Verhalten bisher | Bewertung |
|---|---|---|
| Seite mit `stop` („Anzeigen bis“) | Entfernt nur der Bereinigungs-Cronjob – im Standard **einmal täglich** (`chatbot_purge_interval` = 1440) | Seite bleibt bis zu 24 h in den Antworten |
| Seite mit `start` in der Zukunft | Wird beim ersten Aufruf nach dem Start trainiert | in Ordnung |
| Inhaltselement/Artikel mit `stop` | Kein Cronjob. Contao begrenzt die Cache-Lebensdauer passend (`addSharedMaxAgeToResponse`), neu trainiert wird aber erst beim **nächsten Seitenaufruf** | Wenig besuchte Seiten behalten abgelaufene Inhalte (z. B. ein beendetes Angebot) beliebig lange im KI-Index |
| Inhaltselement/Artikel mit `start` | dito, erscheint erst nach dem nächsten Aufruf | Verzögerung |
| News/Events mit `start`/`stop` | Liste wird beim nächsten Aufruf aktualisiert; Reader teilen sich eine ID (bekannt, `chatbot-optimierungen.md` 2.1) | nicht Teil dieses Ausbaus |

**Lösung:** Neuer Cronjob `ScheduledContentCron` (alle 15 Minuten). Er sucht Seiten, Artikel
und Inhaltselemente, deren `start` oder `stop` seit dem letzten Lauf überschritten wurde:

- Seite abgelaufen/nicht mehr berechtigt → sofort aus dem Index (statt bis zum täglichen Lauf).
- Sonst (Seite oder Inhalt geändert) → die Seite einmal per HTTP abrufen; Contaos Suchindexer
  rendert sie, der `indexPage`-Hook erkennt die geänderte Prüfsumme und trainiert neu.
  Höchstens 20 Seiten je Lauf, Fehler nur ins Log (der nächste Besuch heilt es ohnehin).
- Der Zeitpunkt des letzten Laufs liegt im `cache.app` (nicht in der `localconfig.php`).

## Punkt 7 – Zusatzinhalte

Eigene Backend-Seite (Contao: Modul „Zusatzinhalte“, Tabelle `tl_chatbot_content`;
WordPress: Unterseite „Zusatzinhalte“, Tabelle `{prefix}bluebranch_chatbot_content`).
Ein Eintrag ist entweder **Text** (Textarea für Meta-Infos, beliebig viele Einträge) oder eine
**Datei**. Dateien werden lokal in Text umgewandelt:

| Format | Umwandlung |
|---|---|
| `.txt`, `.md`, `.csv` | gelesen, Zeichensatz nach UTF-8 |
| `.pdf` | `smalot/pdfparser` (reines PHP) |
| `.docx`, `.odt` | `ZipArchive`, XML zu Absätzen |
| `.html`/`.htm` | Tags entfernt |

An die API geht ausschließlich `{externalId: "extra_<id>", title, content, language, type}` mit
`type` `document` (Datei) oder `note` (Text) und **ohne `url`**. Speichern/Aktivieren trainiert,
Deaktivieren/Löschen entfernt. Geänderte Dateien (Prüfsumme) werden vom Cronjob neu übertragen.
Obergrenze 200.000 Zeichen je Eintrag.

**API:** Geprüft – keine Änderung nötig. `TrainContentDto` akzeptiert Inhalte ohne URL, der
JSON-Rumpf darf bis 20 MB groß sein (`main.ts`), `formatChunkContext` lässt die URL-Zeile
weg, und ohne URL im Kontext erzeugt das Modell auch keinen Link. Details im API-Repository.

## Nachtrag 06.10.2026 (Rückmeldungen)

- **Dark-Mode im Contao-Backend:** *Trainierte Seiten* und *Fragen & Feedback* nutzen Contaos
  Farbvariablen (`--text`, `--content-bg`, `--content-border`, …); im Browser geprüft.
- **Wechsel der Art auf „Datei“:** löste über `submitOnChange` ein automatisches Speichern und
  damit eine Übertragung samt Fehlermeldung aus. Jetzt wird bei `SUBMIT_TYPE=auto` nichts
  übertragen. Getestet.
- **Änderungen und Löschen von Zusatzinhalten (Contao), alle gegen eine Mock-API getestet:**
  | Fall | Ergebnis |
  |---|---|
  | Text geändert und gespeichert | sofort neu übertragen |
  | Datei im Dateimanager oder per FTP ersetzt | binnen 15 Min. neu übertragen (Prüfsumme der Datei selbst, nicht `tl_files.hash`) |
  | Lauf ohne Änderung | keine Anfrage an die API |
  | Datei gelöscht | binnen 15 Min. aus dem Index, Eintrag zeigt „Datei nicht mehr vorhanden“ |
  | Eintrag gelöscht | sofort `DELETE extra_<id>` |
  | Eintrag wiederhergestellt (Undo) / Version zurückgespielt | sofort neu übertragen |
  | Deaktiviert | sofort aus dem Index |
  | Unter *Trainierte Seiten* einzeln gelöscht | Eintrag wird deaktiviert (sonst käme er zurück) |
  | „Alle Inhalte löschen“ | aktive Einträge werden beim nächsten Lauf wieder übertragen – wie Seiten beim nächsten Besuch |
  | Entwurf ohne Datei | bleibt unberührt, kein Fehler |
- **WordPress angeglichen:** gelöschte Mediathek-Datei → sofort aus dem Index
  (`delete_attachment`); einzeln gelöscht → deaktiviert. Abgleich geänderter Dateien dort täglich.
- **Reiter im API-Frontend:** *Inhalte* zeigt „Alle / Webseiten / Manuelle Inhalte“ mit Anzahl;
  API-Parameter `kind` und Zählung `counts`. Typecheck/Build/Tests grün, SQL gegen Postgres
  geprüft; die Oberfläche selbst nicht im Browser getestet (lokal laufen API und Datenbank nicht).

## Sicherheits-Review 06.10.2026

Zwei unabhängige Reviews (Contao, WordPress), Befunde gegen den Code geprüft und behoben.

**Contao** – behoben: geschützte Seiten im Index (hoch), CSV-Ausbruch über das Escape-Zeichen,
`pageId`/`moduleId` per HMAC gebunden (ersetzt `chatbot-optimierungen.md` 1.1), XSS über den
Bot-Namen, Ratenlimits und Längengrenzen, Endlos-Parsen fehlerhafter Dateien, Antwortfilter der
Nicht-Stream-Route, Maskierung der Antworten, Umgehung des Protokolls über `summarize`, 24-h-Ablauf
des Verlaufs, Cron-SSRF über den Host-Header, `key=sync` ohne Token, API-Key in Debug-Dateien,
Token-Fallback in der URL, `http://` für die API nur lokal, `json_encode` im Backend-Script.
Live geprüft: echte Antwort, fremde/fehlende Signatur → 403, zu lange Frage → 413, Token-Route
30×200 dann 429, Token in der URL → 403.

**Offen / bewusst nicht geändert:**
- Contao → API und WordPress → API schicken Frage und Verlauf weiterhin als **GET-Parameter**
  (die API kennt nur GET-SSE). Braucht eine POST-Variante der Stream-Routen in der API
  (`chatbot-optimierungen.md` 1.2).
- `?keywords=` (Contao) bzw. `?s=` (WordPress) lösen beim Aufruf automatisch eine KI-Antwort aus –
  präparierte Links zeigen damit eine gesteuerte Antwort auf der echten Domain (Content Spoofing).
- Protokoll ohne Mandantentrennung im Backend: Wer das Modul sehen darf, sieht die Fragen aller
  Startseiten.
- Titel von Zusatzinhalten stehen im `sources`-Ereignis des Streams (im Browser nur ausgeblendet).
- Das Ratenlimit zählt je Client-IP: Hinter einem Proxy muss dieser unter `trusted_proxies` stehen.
